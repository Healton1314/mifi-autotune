# mifi-autotune

给 4G 随身WiFi / CPE 用的**调优工具**：先体检、告诉你能快多少，再一键应用。

纯 Python 标准库，**零第三方依赖**，不刷机、不连厂商云、不需要 root。

```
$ python autotune.py --preview          # ① 体检，输出「现在多少 → 能到多少」
...
========================================================
体检结论
========================================================
  频段：BAND 40 22.9 Mbps  →  最优 BAND 3 48.6 Mbps
        切换后预计 +25.7 Mbps（+112%）
  信道：6（干扰分 2.18）  →  最优 13（干扰分 0.00）
        切换后干扰下降约 100%，主要改善重传和抖动
--------------------------------------------------------
可以优化的项：
  · 频段 BAND 40 → BAND 3
  · 信道 6 → 13

$ python autotune.py --apply-plan        # ② 一键应用，只切一次
[应用] 锁定 BAND 3 …
[√] 已生效，延迟 56ms
[应用] 切换 WiFi 信道到 13 …
[√] 已生效
```

体检期间会断网 2~3 次（切频段实测躲不掉），但**结束后自动恢复原设置**；只有你点了应用才会真的改。

## 为什么需要它

随身WiFi 的实际体验高度依赖**所处位置**，而设备自己的「自动」往往选得很糟：

- **2.4G 信道是公共资源。** 邻居的路由器一开，你昨天"最干净的信道"今天就废了。绝大多数设备出厂默认信道 6，于是几十户人家挤在同一条 20MHz 上。
- **LTE 频段的覆盖和拥塞随地而异。** 设备选频段看的是信号强度，不是速度——信号满格但只有 20 Mbps 是常态，因为那个频段容量被占满了。

手动试一轮要十几分钟，换个地方又要重来。这个工具把「扫描 → 实测 → 排序 → 应用」自动化，每到一个新环境跑一次就行。

## 工作原理

### 一、信道：把邻居折算成分数

对 13 条候选信道各算一个干扰分：

```
score(信道) = Σ  邻居  (信号%/100)² × (重叠宽度 / 20MHz)
```

- 重叠宽度 = `20 - |两者中心频率差|`，只有正重叠才计入；
- 信号项取**平方**而不是线性，因为 90% 的邻居造成的影响远大于 50% 的；
- 分数最低的信道胜出。

### 二、频段：直接实测，不看信号格

逐个锁定频段 → 等重新注册（26 秒）→ 4 路并发下载测带宽 + 10 包延迟 → 排序。无服务的频段直接标记跳过。

### 三、为什么必须多轮

单次测量会被瞬时抖动带偏：一次刚好撞上基站调度空档，就会得出完全错误的结论。所以：

| 项目 | 默认 | 处理方式 |
|---|---|---|
| 信道扫描 | **5 轮** | 同一 AP 出现 ≥2 轮才计入（滤掉幽灵 AP）；信号取多轮**中位数** |
| 频段实测 | **3 轮** | 带宽、延迟取**中位数**，同时输出 `min~max` 看波动 |
| 是否切换 | — | 信道评分改善 <0.30、或带宽提升 <3 Mbps，**就不改** |

最后一行是关键：环境噪声带来的 0.01 分差不会被当成"更优"，否则工具会为了噪声反复折腾你的网络。

轮数可调：`--scan-rounds 7`、`--rounds 5`。

## 平台支持

| 系统 | 信道扫描 | 状态 |
|---|---|---|
| Windows 10/11 | `netsh wlan show networks mode=bssid` | ✅ 已验证。字段名多语言适配（中/英/日/韩/德/法/西/意/葡/俄/繁） |
| **Android（Termux）** | `termux-wifi-scaninfo` | ⚠️ 已实现，需 Termux:API + 定位权限。**可在手机上完全独立运行** |

系统语言不在支持列表里时，工具会**明确跳过信道优化**而不是拿空数据乱改。

### 换不换频段：一条自动规则

只看速度会把人推进「跑分很高但一直在抖」的频段，只看稳定又会让人白白降速。所以默认走一条自动裁决：

| 情况 | 选谁 |
|---|---|
| 一方速度强太多（最差一轮也快 50% 以上） | **选快的**，稍微不稳也认 |
| 速度差不多（中位数差距 10% 以内） | **选更稳的**（波动倍数好 40% 以上才动） |
| 稳定性差不多（波动倍数相差 25% 以内） | **选更快的**（仍要过 3 Mbps 阈值） |
| 两边都差不多 | 什么都不改 |

关键是第 1 条**用「最差一轮」比，不用峰值**：峰值是运气，最差那一轮才是你真会遇到的速度。

两条单线仍然保留，想强制就用 `--strategy`：

```bash
python autotune.py --preview                     # 自动（默认）
python autotune.py --preview --strategy speed    # 只认速度：波动大就干脆不给建议
python autotune.py --preview --strategy stability # 只认稳定：速度差不多就换成更稳的
python autotune.py --apply-plan --dry-run        # 演练：只说会改什么，不碰设备
```

### 频段是「先问设备，再逐个测」

工具不维护一份写死的频段清单，而是**先读驱动声明的 `capabilities()["bands"]`**——设备支持哪些频段，就测哪些，一个不漏。原因很简单：如果候选清单漏了某个频段，那「最优频段」这个结论就是不可信的。

粗测完所有频段后，还会对**分数最高的两个**（最优 + 当前）各补一轮确认。单轮结果容易被基站调度带偏，而这两者的差值正是决策依据，值得多花 90 秒。

嫌慢可以缩小范围：`--bands 3,40` 只测指定频段，`--bands preferred` 只测 `config.json` 里的子集。

### 为什么体检也要断网

因为**设备只能上报当前服务小区的信号，看不到邻区**。想知道别的频段能跑多快，只能切过去实测一次，没有别的办法。

所以体检期间会断网 2~3 次（每次约 30 秒）。但体检结束**一定会切回你原来的设置**——你不点应用，设备就跟没动过一样。真正应用时只切一次，不再重测。

### 其他命令

```bash
python autotune.py                      # 快速检测，不切频段（只扫描 + 测当前延迟）
python autotune.py --apply              # 一步到位：体检并直接应用（跳过人工确认）
python autotune.py --apply --bands all  # 六个频段全测（慢，约 8 分钟）
python autotune.py --wifi-only          # 只优化 WiFi 信道
python autotune.py --lte-only           # 只优化 LTE 频段
python autotune.py --restore            # 还原为「频段不锁定 + 信道自动」
python autotune.py --list-drivers       # 看当前装了哪些设备驱动
python autotune.py --watch              # 进阶：持续挂在后台，劣化才自动重测
```

常用参数：

| 参数 | 说明 |
|---|---|
| `--bands` | `default`=设备声明的全部频段；`preferred`=配置里的子集；或逗号分隔如 `3,40` |
| `--ssid 名称` | 指定自己设备的 WiFi 名，扫描时排除（见下方说明） |
| `--ping-host` | 延迟探测目标，默认 `223.5.5.5` |
| `--speed-url` | 测速下载地址。默认会自动挑一个当前能下动的源（见下方「测速源」） |
| `--rounds` / `--scan-rounds` | 频段测量轮数 / 信道扫描轮数 |
| `--strategy` / `-s` | `auto`（默认，自动裁决）/ `speed`（只按速度）/ `stability`（只按稳定） |
| `--dry-run` | 演练：把 `--apply` / `--apply-plan` 会做的改动打出来，但不碰设备 |
| `--watch-interval` | 持续检测的探测间隔，默认 300 秒 |
| `--watch-cooldown` | 两次自动重测的最小间隔，默认 900 秒 |
| `--watch-dry-run` | 演练：只报告会触发什么，不动设备 |
| `--guard` | **全自动守护**：在动就解锁频段、久坐就选优并锁定（详见下方） |
| `--guard-settle` / `--guard-interval` | 多久不动算「久坐」（默认 600s）/ 采样间隔（默认 30s） |
| `--guard-fast` | 久坐时直接锁当前驻留的频段，跳过选优（省几分钟，不保证最优） |
| `--observe` | 应用后盯多少秒确认稳定（0 = 不盯，默认 90）；多次不通会提示回滚 |
| `--fresh` | 忽略位置记忆、全部重测（隔 7 天以上没来会自动这样做，一般不用手动给） |
| `--here 名字` | 给当前位置起个名字（如 `--here 宿舍`），日志和记忆里都会带上它 |
| `--forget` | 清空位置记忆（搬过家、换过城市之后用） |
| `--mtu` | 探测这条线路的真实路径 MTU（只读，**只能在电脑上用**，见下方说明） |
| `--clean` | 清掉历史运行记录与 `__pycache__`（保留 `config.json` 和面板令牌） |

### 位置记忆：同一个地方不重复踩坑

同一台设备在同一个地方（用 PCI + 运营商识别，`sites.json` 记着）测过几次之后，工具会记住两件事：**这里哪些频段根本收不到信号**、**哪些频段上次跑得最快**。下次再测就不白等那 15 秒的超时，也不用六个频段从头排一遍。

但记忆会**按时间打折**，因为「上次很快」这件事过期得比「这里收不收得到信号」快得多：

| 上次来是多久前 | 怎么处理 | 大概耗时 |
|---|---|---|
| 72 小时内 | 记忆全信，只测「历史最优 + 当前驻留」 | 约 2 分钟 |
| 3 ~ 7 天 | 覆盖照用（跳过从来收不到信号的），但**每个能收到的频段都重新测速** | 约 4 分钟 |
| 超过 7 天 | 整段记忆作废：**一条都不跳，全部重测**（`--fresh` 就是这个效果） | 约 6 分钟 |
| 超过 30 天 | 连这条位置记录一起删掉 | — |

一个地方以前常来、隔了很久没来，中间可能加了基站、拆了基站、邻居换过几轮、晚上八点的人流也完全不同 —— 拿旧的速度数字跳着测，就是把过期结论当答案。所以隔久了就老老实实全测一遍，测完把历史速度数字**直接换成这次的**（不再和旧值取最大），免得那个偏高的旧数字再骗一次快速模式。

位置用 **PCI + 运营商** 认，但**换了频段会换服务小区**：同一张桌子，锁 BAND 40 是 PCI 236，切到 BAND 3 变成 350。要是照 PCI 一条一条记，工具每切一次频段就等于把自己搬了次家，记忆永远攒不起来——而它偏偏一直在切。所以规则是：**同一运营商，且上一次记录在 20 分钟内**，就认作同一个地方（人真走到另一个小区，通常不会二十分钟内又测一遍；切频段只要几十秒）。记录里会留 `aliases`，界面上会写「同一处还见过 PCI 236」，一看就明白为什么只有一条记录。

更要紧的是**一次体检就把同一个地方的每张面孔都记下来**：体检是唯一「人坐在这儿、把每条频段都锁一遍」的时刻，锁 BAND 3 读到 350、BAND 8 读到 401、BAND 41 读到 477 —— 这些都是同一张桌子。以前只记第一轮那个 PCI，剩下的靠 20 分钟窗口碰运气，窗口一过就分家（实机上「锁 3 之后守护认不出宿舍」就是这么来的）。现在每条频段的 PCI 都进 `cells`，隔一个月回来、换哪条频段驻留，都认得出这是同一处。

还有一条**人说了算**的路：`mifi --here 宿舍`。位置靠上面那套推断，推断不出来的场合（第一次来、或者手动锁 3 之后再没切过频段，手上只有一张面孔）就用这个名字当锚。名字只是标签：它让「我记得这里是宿舍」变成一句可核对的话，日志里会写「锁定 BAND 3（宿舍）」；命名不等于测过，该重测还是会重测；`--forget` 会把名字一起清掉。

**守护模式和体检写的是同一本账**（0.7.6 起）。以前守护只在「锁定那一刻」写一次信号，其余时间采到的信号全丢；锁到一条新频段（PCI 跟着变）时，记忆里没有这条记录，采样连门都进不去——于是「守护跑了一早上」和「一次体检」各记各的，回到熟悉的地方照样判不出哪条最优。现在：

- 锁着的时候每 5 分钟把那一下的信号写进当前频段；丢包 ≥15% 时立刻补一条样本。速度那一格留空而不是写 0——守护只 ping 不测速，写 0 等于在记忆里造一条假的「0 Mbps」，日后按速度统计就被带偏。
- 记忆里没有的 PCI 也会建一条**观测记录**：有 `observed`、有小区、有信号，就是没有 `last`。它不代表「测过」，`site_memory_state` 照样判它 stale，不会让过期记忆装成可信记忆；但设备换频段那一刻它会被并进这个位置的本体，不会变成两本账。
- 「设备换频段 / 换小区、人没动」时顺手把两个 PCI 记成同一处，所以锁 BAND 3（PCI 350）攒下的信号，体检在 BAND 40（PCI 236）下也看得见。

另外每 5 次还会强制全测一遍兜底，防止环境变了工具还在照着老记录跳。

### 滚动样本：抓「测不出来」的毛病

一次体检在一个频段上只待 54 秒，所以有两类问题它天生看不见：

- **周期性掉包**——你那个位置 BAND 40 跑 41Mbps，但每 3~5 分钟就丢包 30%~50%，54 秒的窗口根本碰不到
- **时段差异**——晚上八点和凌晨两点不是一回事，而体检只在「你按下回车的那一刻」测过

所以每个频段还会留最近 8 次样本：`[几点, 速度, 丢包%, 延迟]`，滚动覆盖，文件不会随运行次数长大。

攒够样本之后，结论里会多出一句提醒，并且在「快的那个老掉包、旁边有个只慢一点点」的时候改选稳的那个：

```
[!] 掉包记录：BAND 40 过去 5 次里有 40% 丢包 ≥20%，会时不时掉一下；
              BAND 3 只慢 11%，这次选它
```

判据写死成「备选不慢过 15%」——差得太多就不换，掉包固然烦，但慢一半更难受，这种事留给你自己决定。样本少于 2 次不会下这个结论（一次测速说明不了周期）。

**还是不够就手动来**：`--strategy speed` 强制只看速度，`--strategy stability` 强制只看稳定，`--fresh` 忽略全部历史重测。

### 路径 MTU：一个容易被误判成「信号差」的问题

```bash
python autotune.py --mtu      # 只读，约 20 秒，不改设备
```

如果设备的 MTU 设得比这条线路的真实路径 MTU 大，症状是**网页能打开、大文件下载卡住、视频一直缓冲**——这跟「信号差」长得几乎一样，于是很容易反复切频段，而切频段根本治不了它。

检测方法是不分片 ping 二分：从 1472 字节往下试，找出能整包通过的最大值（`ping -f -l` / `-M do`），加上 28 字节包头就是路径 MTU。测出来和设置值比较，给出结论。

两条硬道理：

- **测不出来就说测不出来。** ICMP 被公共网络拦掉时（连 1200 字节都不通），返回的是「测不出来」，绝不编一个数字。
- **只报告，不自动改。** 改 MTU 要重新拨号、断网 30~60 秒，而且改错了可能连设备后台都进不去，不适合跟着体检自动做。

**手机端不支持这一项**，也不打算加：Android 不给普通应用 ICMP 权限，Termux 里的 `ping` 通常拿不到 raw socket，硬做只会给出假数字。这项在手机上会直接跳过，不影响频段体检。一条线路的 MTU 基本不变，用电脑测一次就够了。

## 三道保险（都是踩坑换来的）

### 一、测不准就说测不准，不给你假建议

体检结论里带一个可信度判断。出现下面任一情况，它会明确写「这次结论不可信，先别照它改」，并且**不给**切换建议：

- 当前频段测不出速度（测速源不可用，或该频段几乎没有数据能力）
- 最优频段也不到 3 Mbps（网络整体太差，比较没有意义）
- 某个频段多轮波动超过 4 倍（比如 `[1.0, 31.8]`，这种「最优」纯属运气）

理由很直接：在这种状态下推荐「切过去能快 20Mbps」，会让你白断一次网，还可能更差。

### 二、测速源自动选，不把「源连不上」记成「0 兆」

```bash
python autotune.py --preview
#       [测速源] 自动选用 http://dldir1.qq.com/weixin/Windows/WeChatSetup.exe
```

开工前先花几秒验证测速源真能下到字节，可用才开测；某一轮测出 0 会换下一个源再试。**为什么必须这么做**：实测遇到过整条链路「HTTPS 到各家 CDN 全失败、HTTP 正常」的情况（同一文件 http 能跑 2.9MB/s，https 直接 0 字节），如果只写死一个 https 源，每个频段都会测出 0 Mbps，然后据此推荐一个完全错误的频段。

### 三、中途挂了也把设备还原

体检要反复切频段，如果中途出错（设备失联、Ctrl+C、断网），**`finally` 分支一定会把频段切回你原来的那个**，并在切不回去时明确告诉你「请手动在设备后台把频段改回 BAND x」。

这条是事故驱动的：早期版本在测 BAND 8 时驱动超时崩溃，进程直接退出，设备被留在 BAND 8（丢包 60%），用户当场上不了网。

> 这个保护只有一份实现（`measure_all_bands`），`--preview` 和 `--apply`（也就是 `--watch` 触发的那条路）共用它。以前两处各写一遍，`--apply` 那份漏了 `try/finally`——同一份代码写两遍，迟早只修一处。

### 附：设备会话会自动重建（不用手动开浏览器）

部分 ZTE-RTA 固件在切换频段后会把管理会话踢掉（`login_status=KICKOFF`），而这时 `xml_action.cgi` 不再下发 Digest 挑战。工具会自动走设备自己的 `login.cgi` 重新登录：

```
GET /login.cgi                                   → 拿到 realm / nonce（这个接口在 KICKOFF 下照样给）
GET /login.cgi?Action=Digest&userName=..&nonce=..
    &response=<digest>&qop=auth&cnonce=..&temp=asr → 建立会话
```

所以正常情况下你不需要再手动登录设备后台。只有当密码不是默认值、或设备正忙时才需要人工介入，报错里会写清楚。

## 持续检测（可选，`--watch`）

如果你不想每次手动点，可以让它挂在后台盯着：平时只打 ping，真变慢了才自动重测并切换。

```bash
python autotune.py --watch                          # 默认 5 分钟探一次，15 分钟冷却
python autotune.py --watch --watch-dry-run          # 先演练，只看会不会误报
python autotune.py --watch --watch-interval 600     # 探得更稀一些
```

**它是个常驻进程，所以必须能被你看见、也能被关掉：**

- 面板（`python server.py --lan`）上有独立的「持续检测」卡片：实时显示 `运行中 · 已 N 分 N 秒`、滚动日志，一个按钮开、同一个按钮关
- 每一轮探测都会打印一行（时间 / 延迟 / 抖动 / 丢包 / 基线），开了就是开了，藏不住
- 面板进程退出时会顺带杀掉它，不会留孤儿进程
- 命令行里 `Ctrl+C` 即停；手机键盘上按不出来就另开一个窗口 `mifi --stop`
 （同一 uid 直接按命令行认进程杀掉，守护会走同一条收尾路径，不掉 wake lock）

**为什么不是「每隔几分钟测一次速」**：一次测速要跑几十兆流量，本身就干扰你在用的网络，长期跑不现实。所以平时只打 10 个 ping（几百字节），只有真的异常了，才付出「断网几十秒」的代价去重测。

触发条件（满足任一）：

| 指标 | 阈值 |
|---|---|
| 丢包 | ≥ 3% |
| 延迟 | > `min(260ms, max(基线×1.8, 80ms))` |
| 抖动 | > `min(80ms, max(基线×1.8, 25ms))` |

这个三段式是有意设计的：**下限**保证正常波动不触发（否则一抖动就断网重连）；**倍数**让本来就慢的链路按比例放宽；**上限**防止基线太高时阈值一起飘走、永远触发不了。还没积累基线时（冷启动）用 180ms / 40ms 兜底。

触发后跑一次完整重测并应用，然后进入冷却期（默认 15 分钟），避免在噪声里反复切换——**频繁切频段比不切更伤体验**。

> 「白天好、晚上七八点开始卡」这个场景用它最合适：卡的那一下它自己重测一次，选出当时环境下最快的频段。不想让它自作主张，就只用上面的两步走。


### 全自动守护（`--guard`）

和 `--watch`（发现变慢才重测）不同，守护管的是**位置**：设备出厂逻辑不锁频段，会自己来回跳，跳一次就要重启射频、断网将近 90 秒。守护做的事就这三件：

1. **在动就解锁** —— 锁死一个频段走到没覆盖的地方就是「满格上不了网」
2. **路过不锁，坐满 10 分钟才锁** —— 第 3 分钟先花 20 秒快测一下当前这条，只测不锁
3. **锁定后连不上就先换备选，没备选才解锁** —— 直接交还给设备，它只会按信号最强选回刚才那条

久坐要锁的时候，优先用**这个位置的历史最优**（几乎不断网）。只有记忆里没有可用数据时才跑体检，而**体检跑完一定会真的锁上**——哪怕体检结论是「保持现状、没必要换」，也会把选出的那条锁住。不锁等于什么都没做：白等 10 分钟、白断网六七次，设备下一步照样自己乱跳。（0.7.0 之前就是这样，最后得手动锁，已修。）


### 关于「排除自己的 AP」


扫信道时如果把自己设备的 AP 也算成邻居，就会得出"我当前这条信道很挤"的错误结论——于是把你赶到一条更差的信道上。所以必须排除。

识别顺序：

1. `--ssid` 参数
2. `config.json` 里记住的 `own_ssid`
3. 当前电脑连着的 WiFi 名（走 WiFi 时自动识别）
4. 都没有（例如电脑走 USB）→ 退化为「信号最强的那台大概率是自己」，并会**明确提示你猜的是谁**

第 4 步只是兜底，猜错会明显影响结论。知道自己 SSID 的话，跑一次 `--ssid 你的WiFi名`，之后会记在 `config.json` 里。

## 安全设计

| 措施 | 说明 |
|---|---|
| **默认只读** | 不加 `--apply` 绝不写设备 |
| **改动范围最小** | 只碰 `Prefer_Band` 和 `channel`，其余字段一律回填原值 |
| **自动回滚** | 换频段后 26 秒内无法上网，自动切回原频段 |
| **状态留档** | 改动前写入 `state.json`，`--restore` 一键还原 |
| **失败不改** | 信道写入后读回校验，未生效则恢复原值 |
| **趋势记录** | 每次运行追加 `autotune-log.jsonl`，可用来观察时段规律 |
| **面板鉴权** | 所有 `/api/*` 校验访问令牌，防止同网段的人改你的路由器 |
| **切换冷却** | 守护模式两次重测至少间隔 15 分钟，避免反复断网 |

**注意**：`--apply` 期间会短暂断网（换频段需要重新注册，每个频段约 26 秒；默认测 2 个频段，合计约 4 分钟）。正在下载或开会时别跑。

## ⚠️ 带出门之前请先解锁频段

**这是使用本工具最容易踩的坑，务必读完。**

锁定频段是把设备**钉死在一个频段**上。在宿舍/家里它更快，但换个地方，当地基站可能根本不用那个频段，结果就是：**信号满格却上不了网**，或者直接无服务。而且这个现象很难自己联想到是频段锁的问题。

```bash
python autotune.py --restore     # 出门前跑一次，回到「自动 + 不锁定」
```

回来后想再锁定，跑一次 `--apply` 即可。

不想来回切的话也可以一直不锁——代价是设备自动选的那个频段可能只有锁定方案的 40~50%（看当地哪个频段拥塞）。

其他几项设置（信道、带宽、加密）跟地理位置无关，可以一直留着。

## 架构：引擎与设备解耦

这个项目**不绑定任何具体型号**：

```
autotune.py          引擎：扫描、测量、决策、回滚 —— 不知道设备是什么牌子
scanner.py           2.4G 扫描层：Windows / Linux / macOS 三种来源
probe.py             测速与延迟层：与系统语言无关的解析
      ↓ 只依赖抽象接口
drivers/base.py      DeviceDriver 抽象基类（get_state / set_band / set_channel / capabilities / identify）
      ↓ 具体实现
drivers/zte_rta.py   已验证：ZTE-RTA 固件（飞猫 FM_M1 等）
drivers/template.py  新机型从这里抄
```

引擎只用 `DeviceDriver` 定义的 5 个方法，所以：

- 设备**不支持锁频段**？`capabilities()["can_lock_band"] = False`，引擎自动跳过频段部分，只优化信道。
- 设备**不支持改信道**？同理。
- 设备频段是 **B1/B5/B7** 等其他组合？在 `capabilities()["bands"]` 里声明，引擎不写死频段表。

### 已适配

| 驱动 | 适配范围 | 状态 |
|---|---|---|
| `zte_rta` | ZTE-RTA 固件（`/xml_action.cgi` + Digest，realm=`Highwmg`），如飞猫 FM_M1 | ✅ 已验证 |
| — | 其他 ZTE-RTA 系 CPE / 随身WiFi | 理论可用，欢迎反馈 |

### 怎么适配新机型

判断能不能做，只看一件事：抓一下设备 web 后台的请求，**有没有「读当前频段/信道」和「写频段/信道」的接口**。两个都有就能做，只是字段名不同。

```bash
cp drivers/template.py drivers/yourbrand.py   # 1. 复制模板
# 2. 实现 5 个方法
# 3. 在 drivers/__init__.py 的 DRIVERS 里加一行
python autotune.py --driver yourbrand          # 4. 验证
```

已经知道、但不走这套接口的路线：

- **Qualcomm MSM8916 平台**（UZ801 / UFI-001 等可刷 OpenWrt 的随身WiFi）：用 [msm89xx](https://github.com/ev63nii/msm89xx)
- **华为 HiLink**（E3372 等）：走 `api/hilink` 系列接口
- **已刷 OpenWrt 的设备**：直接用 `uci` / LuCI；本工具的价值在「测量 + 决策」这层，可以只复用 `scanner.py` 与评分逻辑

## 手机面板（PWA）

```bash
python server.py --lan       # 手机和电脑连同一个 Wi-Fi
```

终端会打印类似这样一行，**手机浏览器直接打开它**：

```
手机访问： http://192.168.1.23:8787/?k=Xk3pQ9vLm2Rt
```

iOS/Android 都能「添加到主屏幕」，用起来跟 App 一样。面板上就是三步：

1. **体检并预估** → 跑完显示「频段 X → Y，预计 +N Mbps」「信道 A → B，干扰下降 M%」
2. **一键应用这个优化** → 只切一次，约 30 秒
3. **持续检测**（可选）→ 一个开关，运行中会显示「已运行 N 分 N 秒」和滚动日志，随时能关

另外还有「扫描信道」（只看柱状图，不动设备）和「恢复默认」（带出门前用）。

### 访问令牌（重要）

所有 `/api/*` 都要求令牌，否则返回 401。为什么必须有：

**面板能改设备频段、能让整个网络断线。** 而 `--lan` 是把端口暴露在整个局域网里的——不校验的话，同一 WiFi 下任何人都能操作你的路由器。

- 令牌首次启动时自动生成，存在 `.panel-token`（已加入 `.gitignore`，权限 600）
- 用带 `?k=` 的地址打开一次，令牌会写进 Cookie（HttpOnly），之后正常访问即可
- 也可以自定义：`--token 你的令牌`，或设环境变量 `MIFI_PANEL_TOKEN`
- 脚本调用：请求头加 `X-Panel-Token: <令牌>`

> 即便如此，**别把 8787 端口映射到公网**。这是局域网工具，不是给外网用的。

> ⚠️ 这种方式**依赖电脑一直开着**。想摆脱电脑，看下一节。

```bash
mifi --help       # 这一版支持的全部用法（mifi --help --all 看完整参数表）
```

**运行记录只留最近一次**：每跑完一次，`autotune-log.jsonl` 里的上一条会被替换掉（不是无限追加），`plan.json` / `state.json` 本来就是覆盖写。想多留几份历史就改 `config.json` 里的 `"log_keep": 5`；设成 `0` 就完全不保存。`mifi --clean` 会把这些连同 `__pycache__` 一起清掉，但**保留 `config.json` 和面板令牌**。

**三个手机上特有的点**：

- **换频段时「上网」会断 30 秒左右，但手机和设备的 WiFi 不会断**（设备的 AP 不依赖移动网络），所以体检不会失联，测完会自动切回原频段。
- 安卓普通应用拿不到 ICMP，`ping` 也用不了。工具会自动改用 **TCP 握手耗时**测延迟（`probe._tcp_latency`），不影响判断。
- 想扫周边 WiFi 需要装 Termux:API 并给**定位权限**（安卓 10+ 把 WiFi 扫描算作位置信息）。拿不到就跳过信道优化，**频段优化不受影响**。MIUI/HyperOS 记得给 Termux 关掉省电限制。

> 信道扫描失败时不会再甩一句「没权限」了：`mifi --scan` 会先用 `termux-battery-status` 探一下 Termux:API 这座桥通不通——桥不通说明是**App 没装/被冻结**，桥通着但扫描超时才是**定位权限**问题，两种情况给的动作完全不同。

### 方案 B：扔到一台常开的小机器上

树莓派、软路由、NAS 都行，只要它连在这台随身WiFi 的网里：

```bash
python server.py --lan
```

手机从任何地方访问它即可——这是真正「永远在线」的做法，也最省心。

> 想从**外网**访问，别直接把 8787 映射出去（明文 HTTP）。用 Tailscale / ZeroTier 这类组网工具。

## 接口备忘

给想适配其他机型的开发者：

```
GET  /xml_action.cgi?method=get&module=duster&file=wan
GET  /xml_action.cgi?method=get&module=duster&file=uapxb_wlan_basic_settings
GET  /xml_action.cgi?method=get&module=duster&file=status1
POST /xml_action.cgi?method=set&module=duster&file=wan
POST /xml_action.cgi?method=set&module=duster&file=uapxb_wlan_basic_settings
```

三个坑（都踩过）：

1. Digest 认证的 `uri` 字段必须写成 **`/cgi/xml_action.cgi`**，与实际请求路径 `/xml_action.cgi` 不一致，按实际路径算会一直 401 / 空响应。
2. **未认证的 POST 会被设备直接 reset 连接**，必须先发一个 GET 取到 `nonce`，再带认证发 POST。
3. 公开接口（如 `file=locale`）**不返回认证挑战**，不能用它取 `nonce`，要用需要认证的 `wan` / `status1` 探测。

字段：`Prefer_Band`（0 = 不锁定，否则填 LTE 频段号如 3/40）、`channel`（0 = 自动，1–13）、`bandwidth`（1 = 20MHz，2 = 40MHz）。

## 局限（说清楚，别抱错期待）

- **只能优化到硬上限为止。** 4G CAT4 设备的空口上限就那么大，晚高峰基站拥塞属于运营商侧问题，任何设备设置都救不了。
- **不绕过运营商限速。** 签约速率（QoS）绑在 SIM 卡上，设备侧改不了；本工具也不做这类事。
- **不处理 5G WiFi。** 只扫 2.4G，因为多数随身WiFi 是单频 2.4G 设备。
- **不改信道带宽和加密。** 属于策略问题，交给用户自己决定。
- **切换会断网。** 这是切频段的物理代价，无法避免。

## English

**mifi-autotune** automatically finds the best LTE band and 2.4GHz WiFi channel for your 4G dongle / MiFi / CPE — it scans neighbouring APs, measures each band with multiple rounds, and applies the winner.

- Zero dependencies (Python 3.8+ standard library only)
- Read-only by default; `--apply` to write. Auto-rollback if the new band can't get online
- `--watch` daemon mode: cheap latency probing, full re-measure only when the link actually degrades
- Driver-based: the engine knows nothing about brands. `drivers/zte_rta.py` is verified; copy `drivers/template.py` to add yours
- Ships with a local PWA dashboard for your phone (`python server.py --lan`), protected by an access token
- `pip install .` gives you `mifi-autotune` and `mifi-panel` commands

```bash
python autotune.py            # report only
python autotune.py --apply    # measure and apply
python autotune.py --watch    # keep watching, re-tune when it degrades
python autotune.py --restore  # unlock band + auto channel  ← do this before travelling
```
